# Отправка файлов на сайты: локальная проверка

29 октября 2026. Локальная сборка без публикации и изменения версии.

## Поведение

- Нажатие на HTML `input type=file` открывает системный `NSOpenPanel` как sheet своего веб-окна. Параметры WebKit определяют выбор одного/нескольких файлов и режим папок (`webkitdirectory`). В сообщении диалога показан origin запрашивающего frame, включая схему и нестандартный порт.
- Основные и открытые сайтом окна используют тот же WKUIDelegate. Выбранные file URL передаются в штатный completion WebKit. Приложение не читает и не копирует содержимое файлов, не ведёт историю отправок и не повторяет HTTP-запрос через URLSession. Нативная панель может хранить свои стандартные системные настройки.
- Отмена возвращает WebKit `nil`. Переход страницы, закрытие окна или демонтаж WKWebView отменяют незавершённый выбор. Completion разрешается ровно один раз, в том числе если нативное завершение sheet приходит позже отмены. Перед передачей URL дополнительно проверяется, что WKWebView всё ещё принадлежит той же активной сессии.
- Перетаскивание остаётся нативным поведением WKWebView: приложение не подменяет `DataTransfer`, не добавляет HTML drop-перехватчики и не закрывает веб-страницу собственным drop overlay. Один или несколько файлов можно бросать на file input или в область загрузки, которую поддерживает сайт. Наличие произвольного drop zone зависит от самой страницы.
- Навигации на `file:` внутри страницы отменяются. Поэтому файл, брошенный вне поддерживаемой области загрузки, не должен передаваться внешней программе через прежнюю общую обработку нестандартных схем. Входящие ссылки для предпросмотра по-прежнему ограничены HTTP(S), исходная ссылка для передачи браузеру сохраняется.
- Публичный `WKOpenPanelParameters` сообщает multiple/directories, но не список HTML `accept`. Собственная фильтрация типов в диалог не добавлена; правила и проверка принимаемых файлов остаются у сайта/WebKit.

## Автоматическая проверка

Обязательная команда:

```sh
xcodebuild -project Linklet/Linklet.xcodeproj -scheme Linklet -sdk macosx test CODE_SIGNING_ALLOWED=NO
```

Полный прогон: **118 тестов, 0 ошибок**, `TEST SUCCEEDED`.
Лог: `/tmp/linklet-upload-full-tests.log`.

Пять новых интеграционных проверок работают с настоящими WKWebView и локальным HTTP-сервером:

1. Системный delegate получает реальные параметры file input. В тестовом варианте панели выбираются временные файлы, после чего WebKit создаёт настоящие FileList, читает байты и отправляет multipart POST. Проверены single/multiple в основном и всплывающем окне, бинарное содержимое, cookies, ровно один запрос на отправку и неизменность URL страницы/исходной ссылки.
2. Выбор каталога через `webkitdirectory`: WebKit перечисляет вложенные файлы с относительными путями; отмена не добавляет файлов и ничего не отправляет.
3. Настоящий NSOpenPanel прикрепляется к нужному окну и закрывается при навигации и закрытии источника.
4. Модель нативного `NSDraggingInfo` с отдельным pasteboard передаёт реальные временные file URL в зарегистрированный AppKit drag destination WebKit. Выполняются draggingEntered/Updated, prepare/perform/conclude. Затем проверяются FileList, чтение содержимого файла и multipart POST из HTML drop zone в основных и всплывающих окнах. JavaScript не создаёт подставные File/DataTransfer для этого теста. Это проверка нативного пути AppKit → WebKit → DOM, а не физического движения мыши между Finder и приложением.
5. Настоящая navigation policy отменяет file URL и не вызывает обработчик открытия внешнего приложения. Проверка ожидает решение delegate, без фиксированной задержки для результата.

Тестовые файлы и HTTP-запросы содержат только созданные тестом данные; реальные пользовательские документы и сторонние сервисы не используются. Фактический запуск выполнен на текущей macOS. Поведение минимально поддерживаемой macOS отдельно не проверялось.

## Проверка владельцем

1. Полностью завершить Linklet и заменить его тестовой сборкой `build/WindowPreview/Linklet.app`, bundle ID `Linklet`. Настройки сохраняются; установленное приложение автоматически не заменяется.
2. На нужном сайте нажать «Прикрепить»: проверить выбор одного/нескольких файлов, origin в диалоге и отмену без изменения страницы.
3. Перетащить тестовый файл из Finder на область загрузки сайта, затем несколько файлов. Проверить появление вложений и их отправку. В системный диалог выбора можно использовать обычные действия Finder/NSOpenPanel.
4. Повторить выбор и перетаскивание в окне, открытом самим сайтом.
5. Пока диалог открыт, закрыть исходное окно или перейти на другую страницу: незавершённый выбор должен отмениться.
6. На сайте с выбором папки проверить относительные пути и вложенные файлы.

Документация: [WKUIDelegate open panel](https://developer.apple.com/documentation/webkit/wkuidelegate/webview(_:runopenpanelwith:initiatedbyframe:completionhandler:)), [WKOpenPanelParameters](https://developer.apple.com/documentation/webkit/wkopenpanelparameters), [NSOpenPanel](https://developer.apple.com/documentation/appkit/nsopenpanel), [NSDraggingInfo](https://developer.apple.com/documentation/appkit/nsdragginginfo).

## Диагностика зависания YouTube на 0%, 3 ноября 2026

Сообщение владельца поступило после выдачи сборки 1.8 (36); версия установленного приложения отдельно не проверена. Причина на самом YouTube пока не подтверждена: запросы авторизованной страницы и ошибки её JavaScript не получены. Реальные пользовательские видео на сторонние сервисы при диагностике не отправлялись.

Добавлена локальная интеграционная проверка `testPickedFileUploadsRawAndInWorkerChunks`: выбранный через delegate файл с синтетическими байтами размером 3 МБ + 17 байт передаётся целиком через fetch, а затем четырьмя частями через XMLHttpRequest из настоящего Web Worker. Проверяются события прогресса и точное совпадение всех отправленных байтов. Файл имеет расширение `.mp4`, но это проверка транспорта, а не декодирования видео. Сценарий проходит на macOS 27.2; он не воспроизводит весь протокол YouTube, многогигабайтные видео или файлы облачных провайдеров.

Отдельный временный диагностический сценарий выявил проблемы системного WebKit с выбранным File и IndexedDB: в приватном профиле запись завершилась `UnknownError: Error preparing Blob/File data to be stored in object store`; в чистом постоянном профиле запись и чтение прошли, но последующий multipart POST содержал пустое тело при правильном `File.size`. Последний симптом соответствует [WebKit bug 319985](https://bugs.webkit.org/show_bug.cgi?id=319985). Использование именно этого пути загрузчиком YouTube пока не установлено. Созданный для проверки отдельный профиль удалён; профиль владельца не менялся.

Подмена File/FormData, копирование видео в память и изменение настроек хранения не добавлялись. Для следующего шага нужны результат повторной загрузки без AdGuard, размер и расположение файла, а также результат отправки того же файла в Safari или Chrome. В исходном коде приложения изменений пока нет; новая сборка с исправлением этого зависания не заявляется.

Обязательный полный прогон после добавления проверки: **178 тестов, 0 ошибок**, `TEST SUCCEEDED`. Лог: `/tmp/linklet-upload-diagnostic-full-tests.log`.

## Получение сетевых ошибок в диагностической сборке 37

Обычная сборка оставляет инспекцию выключенной. Отдельная диагностическая
сборка компилируется с `SWIFT_ACTIVE_COMPILATION_CONDITIONS='$(inherited) LINKLET_WEB_INSPECTOR'`.
Она включает публичный `WKWebView.isInspectable` и, при наличии соответствующего
селектора WebKit, `developerExtrasEnabled` через KVC для локального пункта
«Проверить элемент». Это SPI WebKit, поэтому дополнительно остаётся публичный
путь через Safari → Develop → текущий Mac → Linklet → нужная страница.
Основные окна и окна, созданные сайтом, включают инспекцию одинаково.
Режим не сохраняется в пользовательских настройках и не меняет загрузчик сайта.
В диагностической сборке потеря фокуса и скрытие приложения не закрывают
веб-окна автоматически: загрузка может продолжаться при переходе в чат.

1. Запустить диагностический `Linklet.app` после завершения предыдущей копии.
2. Открыть YouTube Studio, вызвать контекстное меню страницы → «Проверить элемент».
3. В инспекторе открыть Network/«Сеть», включить сохранение журнала при переходах.
4. Повторить выбор видео. Посмотреть первый запрос загрузки, его состояние/код
   ответа, размер отправки и сообщения Console/«Консоль». Повторную отправку
   пользовательского файла выполняет владелец.
5. Если зависание повторилось, осматривать это окно и инспектор без перезагрузки.

Уже прошедшие запросы текущего старого окна восстановить через новую сборку
невозможно: для полного журнала воспроизведение начинают с открытым инспектором.

Справка: [публичная инспекция WebKit](https://webkit.org/blog/13936/enabling-the-inspection-of-web-content-in-apps/),
[приватные настройки WebKit](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKPreferencesPrivate.h).

Проверка сборки 37: обычный и диагностический полные прогоны прошли по 178
тестов без ошибок (`/tmp/linklet-1.8-37-tests.log`,
`/tmp/linklet-1.8-37-inspector-tests.log`). После изменения обработки потери
фокуса только для диагностического AppDelegate повторный обычный полный прогон
дал две ошибки в нативных тестах фокуса (не получен первый didBecomeKey;
тестовое приложение неактивно при проверке mousemove). Оба теста отдельно
повторены успешно: `/tmp/linklet-1.8-37-focus-retry.log`.
Ручная проверка инспектора в отдельной копии с чистым профилем не завершена:
инструмент управления окнами вернул тайм-аут после знакомства/быстрого поиска.
Это ограничение проверки; запросы реальной загрузки YouTube ещё не получены.

## Осмотр реального YouTube, 4 ноября 2026

В установленной диагностической сборке 37 инспектор удалось открыть через
«Проверить элемент». Зафиксированы следующие результаты без перезагрузки
страницы и без ручного повторения отправки видео агентом:

- XHR к `upload.youtube.com` с `X-Goog-Upload-Command: upload, finalize` и
  offset 0 завершается без HTTP-ответа примерно через 6,97–6,99 секунды:
  `Failed to load resource: Сетевое соединение потеряно`.
- Служебные запросы той же сессии отвечают HTTP 200; ответ содержит
  `x-goog-upload-status: active` и `x-goog-upload-size-received: 0`.
- В системном журнале именно сетевого процесса Linklet начало отправки в
  00:17:32.817 сопоставлено с ошибкой того же resourceID в 00:17:39.763:
  `NSURLErrorDomain -1005`, `NSPOSIXErrorDomain 57`, `Socket is not connected`.
  Непосредственно перед этим QUIC сообщает `85:Network blackhole detected`.
  WebKit помечает ошибку как не Service Worker и не Access Control.
- Владелец подтвердил: тот же файл через Arc загружается.

Это основание проверить транспорт QUIC/WebKit, а не подтверждение первоначальной
гипотезы об IndexedDB. Не доказано, какой именно компонент вызывает потерю QUIC.
Полные URL с параметрами сеанса, содержимое файлов и HAR в репозиторий не внесены.
В текущем системном списке флагов WKPreferences переключатель HTTP/3 не найден.

## Проверочная сборка 38: HTTPS через TCP

Собирается с флагами `LINKLET_WEB_INSPECTOR LINKLET_TCP_UPLOAD_DIAGNOSTICS`.
`DiagnosticUploadTransport` запускает listener только на 127.0.0.1 со случайным
портом и применяет публичную `WKWebsiteDataStore.proxyConfigurations` с
`matchDomains = ["upload.youtube.com"]`. Настройка применяется до первой
навигации и не заменяет уже заданный прокси хранилища.

Listener принимает только CONNECT на точный `upload.youtube.com:443`; upstream
фиксирован тем же адресом. После CONNECT байты проходят без интерпретации и
изменения: сертификат YouTube и TLS проверяет сам WebKit. Секреты, заголовки и
содержимое видео не записываются туннелем. Используются utility queue,
backpressure, блоки не больше 64 КБ, не больше 16 подключений и 15 секунд на
установление туннеля. Закрытие одного направления передаётся как half-close,
чтобы не потерять ответ сервера после отправки тела.

Режим включается только отдельным флагом сборки и не меняет системный прокси,
сертификаты, исходные URL, cookies, режим хранения сайтов или HTTP-запросы.
Это A/B-проверка транспорта, а не подтверждённое исправление YouTube. Для
подтверждения владелец повторяет отправку в этой сборке с открытым инспектором.

Локальные тесты `DiagnosticUploadTransportTests` проверяют отказ посторонним
адресам/портам и обычному HTTP, ограничение заголовка, фрагментированный CONNECT,
точную передачу 3 МБ + 17 байт и ответа, ограничение прокси одним доменом и
сохранение существующей конфигурации. Внутри тестового туннеля используется
локальный HTTP fixture; TLS и реальная загрузка проверяются отдельно при
воспроизведении владельцем.

Полные прогоны сборки 38: **181 тест, 0 ошибок** в обычном режиме и **181 тест,
0 ошибок** с `LINKLET_WEB_INSPECTOR LINKLET_TCP_UPLOAD_DIAGNOSTICS`.
Логи: `/tmp/linklet-1.8-38-tests.log`, `/tmp/linklet-1.8-38-tcp-tests.log`.
